# 移动端批量导出内存溢出方案

## 现象

- iPhone Safari 上传 7 张高清图（如 48MP HEIC）后：
  - **单张不加 LUT**：能正常导出
  - **单张加 LUT**：页面自动刷新（进程被杀）
  - **批量 ZIP 导出**：页面自动刷新，两次后 Safari 提示「页面多次出现问题」
- 桌面端 Chrome 正常

## 根因：移动端内存超限（Jetsam 杀进程）

不加 LUT 能导出、一加 LUT 就炸——这个差异就是定位关键。

### 内存测算（以单张 48MP / 8000×6000 为例）

RGBA 每像素 4 字节，**单张解码位图 = 8000 × 6000 × 4 ≈ 192 MB**。

#### 常驻内存（7 张图全部加载后）

| 项目 | 单张 | 7 张合计 |
|------|------|---------|
| `ImageItem.img`（解码位图） | 192 MB | ~1344 MB |
| `ImageItem.originalBuffer`（原始 HEIC/JPEG 压缩数据） | ~10 MB | ~70 MB |
| `thumbDataURL` 缩略图 | 忽略 | 忽略 |
| PreviewPanel WebGL 纹理（仅当前图） | 192 MB | 192 MB（共享） |
| 3D LUT 纹理（33³ × RGB16F） | — | ~216 KB |
| **合计** | — | **~1.6 GB** |

#### 单张 LUT 导出瞬时峰值

| 项目 | 大小 | 说明 |
|------|------|------|
| `prepareUploadSource` 临时 canvas | 192 MB | 上传源归一化 + 降采样（LUT 路径独有） |
| WebGL 离屏画布（LUT 输出） | 192 MB | `lutCanvas` |
| 输出画布 `outCanvas` | 192 MB | 画水印 |
| `toBlob` 中间缓冲 | ~50 MB | 视格式/质量 |
| EXIF 注入 Uint8Array 拼接（before + after 双份） | ~192 MB×2 | 新 PNG/JPEG 全量复制 |
| **合计峰值** | **~900 MB** | 叠加常驻 ≈ **2.5 GB** |

#### 不加 LUT 的路径（能成功）

没有 WebGL 纹理 + 没有 `prepareUploadSource` canvas，少掉 ~384 MB，瞬时峰值压在 500 MB 以内，叠加常驻约 2.1 GB，刚好在 iOS Safari 容忍阈值内。

#### ZIP 批量导出（更炸）

JSZip 在内存中累积全部 7 张成品 Blob + 压缩中间缓冲，峰值再叠加 200~500 MB，直接超出阈值。

### iOS Safari 的内存限制

- iOS 对单个 WKWebView / Safari 标签页的 Jetsam 内存上限约 **2~3 GB**（取决于设备型号和系统版本，iPhone 16 Pro 约 3 GB）。
- 超过阈值后系统直接杀进程，表现就是「页面自动刷新」。
- JS 堆只是其中一部分，**GPU 纹理、Canvas 位图、Image 位图都算在进程内存里**，`performance.memory` 看不到这些，最容易被忽略。

## 方案分级

### 方案零（最大单一抓手，立即上）—— 预览降采样，不影响导出质量

**这是节省内存最多的一档，也是根因所在**：当前 7 张 48MP 图全量解码常驻，预览区显示才 400~500 px 宽，纯浪费。

**做法**：`ImageItem` 增加 `previewImg`（长边 2048px，约 4~12 MB/张），预览/LUT 预览都用 `previewImg`；导出时才用原 `img`。

| 项目 | 当前（全量 img） | 预览降采样后 | 节省 |
|------|-----------------|-------------|------|
| 单张位图内存 | 192 MB | ~12 MB | 180 MB |
| 7 张合计 | ~1344 MB | ~84 MB | **~1260 MB** |
| WebGL 预览纹理（当前图） | 192 MB | ~12 MB | 180 MB |

**预估常驻内存从 ~1.6 GB 降到 ~300 MB**，直接腾出 1.3 GB 给导出峰值用。

**对用户体验的影响**：
- 预览画布、LUT 实时调整 —— 完全无感知（屏幕上看不出 2048 vs 8000 的区别）
- 导出 —— 仍用原图，**画质无损**
- 首次加载 —— 比全量解码更快（画 2048 比画 8000 快）

**改动点**：
- `ImageItem` 加 `previewImg: HTMLImageElement` 字段。
- `loadImageFromFile` / HEIC 转换后，额外生成一张长边 2048 的预览版（Canvas2D drawImage 缩放）。
- `PreviewPanel`、`useLut`（预览路径）改用 `previewImg`。
- `exportComposedBlob` 继续用原 `img`。

### 方案一（与方案零一起做，双保险）—— 导出路径降峰值

**核心抓手：导出路径的中间 canvas 显式释放 + EXIF 注入零拷贝。**

1. **`exportComposedBlob` 内显式释放画布**
   - `toBlob` 拿到结果后，立即把 `lutCanvas`、`outCanvas` 设 `width = 0` 并置 `null`，触发 GPU/CPU 内存立即回收（不等 GC）。
   - 顺序：拿到 blob → 清 lutCanvas → 清 outCanvas → 再走 EXIF 注入。

2. **EXIF 注入改「零拷贝拼接」**
   - 现在的 `injectExifToJpeg` / `injectExifToPng` 是 `slice(before) + slice(after) + new Uint8Array`，同时存在 3 份完整像素数据。
   - 改用 `new Blob([beforeBytes, exifChunk, afterBytes])`，Blob 底层不拷贝，直接引用原始 buffer。
   - **峰值直接减 ~384 MB**（少了完整复制的那份）。

3. **批量导出每张之间让出主线程 + 主动 GC 时机**
   - `handleDownloadAll` 每张生成完、塞进 zip 后，立即把本地 `blob` 引用置 `null`。
   - 保留现有的 `await setTimeout(0)` 让浏览器有机会做增量 GC。

**预期**：单张 LUT 导出峰值从 ~900 MB 降到 ~300 MB。

### 方案二（中期，超高清兜底）—— 导出降采样

1. **导出安全分辨率**：单张 > 12 MP（或可配置）时导出自动降采样到 12 MP。
   - 12 MP ≈ 4000×3000 ≈ 48 MB 位图，内存是 48MP 的 1/4。
   - 手机/社交分享完全够用，用户感知不到差异。

2. **加「导出画质」开关**：原图 / 高清 12MP / 标清 4MP，用户自选。

**注意**：方案零已经把常驻压到很低了，方案二只在「用户特意选原图 + 批量 9 张 48MP」这种极端场景才需要。

### 方案三（极端场景兜底）—— 批量 ZIP 改流式 / 分片下载

1. **多张 ZIP 不堆内存**：每张生成完立即触发单独下载（批量下载模式），不打包 zip。
2. 或用流式 zip 库（如 `@zip.js/zip.js` + `WritableStream`），边生成边压边写。

## 推荐落地顺序

1. **先做方案零**（预览降采样，1 天工作量）：常驻内存从 ~1.6 GB → ~300 MB，**直接解决 80% 的问题**，且不影响导出画质、用户体验无感知。性价比最高。
2. **同时做方案一**（导出峰值优化，半天工作量）：双保险，把导出瞬时峰值也压下来。
3. 方案零 + 方案一做完后，如果仍有极端场景（9 张 48MP + 批量 ZIP + 原图导出）再考虑 **方案二** 导出降采样开关。

## 验证方式

- **Safari 开发菜单 → 「开发」→ 选择设备 → 「显示 Web 检查器」**，Timelines → Memory 看导出前后的内存曲线。
- 或用 `performance.memory` 粗略看 JS 堆（注意看不到 GPU/Image 位图，仅作参考）。
- 实测 7 张 48MP HEIC，分别测：单张无 LUT / 单张有 LUT / 批量 ZIP 有 LUT，均不闪退为通过。

# 实施记录（方案零 + 方案一 + 惰性解码）

> 状态：**已实现**。以下是最终落地的改动逻辑与代码落点，供 code review。
> 说明：方案零最初设计为「仅加 previewImg」，review 后发现它没释放全分辨率位图、常驻几乎不降。最终改成**惰性解码**（pixelBlob 常驻 + 导出按需解码 + 用完释放），这才是真正把常驻内存打下来的抓手。

## 总体原则

- **导出画质零损失**：`exportComposedBlob` 的输入始终是全分辨率原图，水印按原图画。
- **全分辨率位图不常驻**：常驻的只有压缩源 `pixelBlob`（~10-20MB）和 2048px 预览图，192MB 解码位图只在导出那一刻短暂存在。
- **预览画质无感知**：预览用 2048px 长边，手机屏显示完全看不出差异。
- **禁静默降级**：所有能力降级都有横幅/报错提示，这一点没改。

## 核心改动：惰性解码（真正的内存抓手）

### 底层逻辑

`img`（全分辨率解码位图）之所以占 192MB，是因为它是**解压后的逐像素位图**（8000×6000×4 字节），不是上传看到的 10-20MB 压缩文件（压缩比 9.6~24 倍）。之前每张图都解码后常驻，7 张 48MP 就是 ~1344MB，直接顶到 iOS Safari 的 Jetsam 上限。

**解法**：只常驻压缩源 `pixelBlob`，导出那一刻才 `loadImageFromBlob` 按需解码，用完 `releaseImage` 立即释放。

### 数据流

```
上传 → 解码临时全分辨率 img → 生成 previewImg（2048 白底 JPEG）→ 释放 img
     → 常驻：pixelBlob（压缩源）+ previewImg（预览）
导出 → loadImageFromBlob(pixelBlob) 临时解码 → exportComposedBlob → releaseImage 释放
```

### 改动文件与逻辑

#### 1. `src/types/index.ts` — 类型定义

`ImageItem` 不再持有全分辨率 `img`，改为：

```ts
pixelBlob: Blob          // 全分辨率压缩源（JPEG/PNG Blob），导出时按需解码
previewImg: HTMLImageElement  // 预览降采样图（长边 2048 白底 JPEG，常驻）
```

`width` / `height` 仍为原图像素（信息栏展示给用户看）。

#### 2. `src/utils/index.ts` — 工具函数

- `loadImageFromBlob(blob)`：从压缩 Blob 按需解码全分辨率原图（objectURL，用完 revoke）。
- `releaseImage(img)`：`img.src=''` + 清 handler，把解码位图从内存赶出去。
- `makePreviewImg(img, 2048)`：长边 2048 白底 JPEG（`imageSmoothingQuality='high'`），**一律拍平白底、返回新 Image**，不保留 alpha。
- `flattenToWhite(img)` / `canvasToJpegBlob(canvas, 0.95)`：PNG 拍平 + 高质量 JPEG 编码。
- `loadImageFromFile` / `loadImageFromDataURL` 返回 `pixelBlob`，生成 previewImg 后**立即 `releaseImage(img)`**。

#### 3. `src/composables/useWatermark.ts` — 写入 imageList

`addFiles`（普通 + HEIC 路径）和 `addImageFromDataURL` push 时存 `pixelBlob`（而非 `img`）。

#### 4. `src/components/PreviewPanel.vue` — 预览改用 previewImg

所有渲染路径（`renderLutToOffscreen` / `render` / `refreshWatermark`）用 `previewImg` + `previewImg.width/height`。信息栏 `sizeText` 仍显示原图像素。

#### 5. `src/views/HomeView.vue` — 导出按需解码

`handleDownload` 和 `handleDownloadAll` 改为：

```ts
const fullImg = await loadImageFromBlob(item.pixelBlob)
try {
  // exportComposedBlob({ img: fullImg, ... })
} finally {
  releaseImage(fullImg)  // 用完立即释放，峰值只有 1 张大图
}
```

## 附带优化：HEIC 与 PNG 的体积/透明处理

### HEIC → 高质量 JPEG（不再转 PNG）

`heicConvert.ts`：`heicToPng` → `heicToJpg`（`image/jpeg` + `quality 0.95`）。

**原因**：HEIC 是导出源，转 PNG 会得到 ~120MB 的无损 PNG 常驻；转 quality 0.95 的 JPEG 只有 ~15MB，常驻省 8 倍。0.95 视觉无损，肉眼不可见差异。

### PNG 一律拍平非 alpha

- 照片/截图带 alpha 的 PNG，透明区域在 JPEG 导出时会变黑。源头统一 `flattenToWhite` 拍平到白底。
- `pixelBlob` 对 PNG 输入也改成「拍平后的 JPEG」，不再保留 alpha 通道，体积也更小。
- `makePreviewImg` 一律白底，与导出 JPEG 铺白底（`exportWithLut.ts`）对齐。

## 方案一：导出路径降峰值

### 第 1 项：EXIF 注入零拷贝（最大收益）

**问题**：之前 `injectExifToJpeg` / `injectExifToPng` 的做法是 `FileReader.readAsArrayBuffer` 把整张新生成的图片读进内存，然后 `new Uint8Array` 做 before + exif + after 的字节级拼接。拼接时内存里同时存在 3 份完整像素数据（before/after 是切片 + result 新数组），48MP 下约多占 ~576 MB 峰值。

**改法**：只读取文件头部 32 字节定位插入点，用 `Blob.slice()` 切出 before/after，最后 `new Blob([before, exifChunk, after])`。Blob 的底层是引用计数 + 指针，不拷贝像素数据。

改动文件：`src/utils/index.ts`

`injectExifToJpeg` 改动要点：
- `readAsArrayBuffer(newJpegBlob.slice(0, 32))` —— 只读前 32 字节，够解析 SOI + APP0 长度。
- `const before = newJpegBlob.slice(0, insertAt)`，`const after = newJpegBlob.slice(insertAt)`。
- `resolve(new Blob([before, app1, after], { type: 'image/jpeg' }))` —— app1 是 Uint8Array（几 KB），Blob 构造函数能直接接受。

`injectExifToPng` 改动同理：
- 只读前 32 字节，够解析 PNG 签名 + IHDR length 字段。
- `Blob.slice()` + `new Blob([before, exifChunk, after])`。

**峰值收益**：EXIF 注入阶段从「3 份全图」降到「1 份全图 + 几十 KB」，省约 384 MB（48MP 情况）。

### 第 2 项：导出画布显式释放

**问题**：`exportComposedBlob` 里 `lutCanvas`（LUT 输出）和 `outCanvas`（水印叠加）两张全分辨率画布，在 `toBlob` 完成后、函数 return 之前一直占着内存。EXIF 注入阶段它们还活着，等于又多了两份全图。

**改法**：`toBlob` 拿到 blob 后，立即：

```ts
outCanvas.width = 0
outCanvas.height = 0
outCanvas = null
lutCanvas.width = 0
lutCanvas.height = 0
lutCanvas = null
```

然后再走 EXIF 注入。

改动文件：`src/utils/exportWithLut.ts`

为什么设 `width = 0` 有用：
- Canvas 2D 的 backing store 像素数据，在 `canvas.width` 改变时会立即释放并重新分配。设 0 会立即释放位图内存。
- 单纯置 null 只是去掉 JS 引用，要等 GC 才释放；设 width=0 是主动释放。
- WebGL 画布（`lutCanvas` 在有 LUT 的路径上）的 GPU 纹理/帧缓存，设 width=0 也会触发 context 重新分配，释放旧的 GPU 内存。

类型声明上的小改动：
- `let lutCanvas: HTMLCanvasElement | null = null`
- `let outCanvas: HTMLCanvasElement | null = document.createElement('canvas')`
- 使用处加非空断言 `!`（逻辑上保证此时非空）。

**峰值收益**：EXIF 注入阶段少占两份全图位图 + GPU 纹理，省约 384 MB。

### 第 3 项：批量导出每张释放引用

改动文件：`src/views/HomeView.vue` → `handleDownloadAll`

- `exportComposedBlob` 的返回值命名为 `result`（不是解构为两个变量，方便整体置 null）。
- `zip.file(outName, result.blob)` 后立即 `result = null`，释放本地引用。
- 保留 `await setTimeout(0)` 让出主线程，给浏览器增量 GC 时机。

说明：JSZip 内部仍然持有 blob 引用（要等 zip 全部生成完才释放），所以这项的收益是「让闭包内临时变量不意外延长生命周期」，属于兜底性改动。真正决定 ZIP 峰值的是 JSZip 本身的内存模型——这是方案三流式 zip 要解决的，方案一不碰。

### 第 4 项：LUT 上传源临时 canvas 释放

改动文件：`src/utils/lutRenderer.ts` → `uploadImage`

`prepareUploadSource` 每次都会新建一张与图片同尺寸的 Canvas2D（48MP ≈ 192MB），用于色彩管理归一 + 超限降采样。`gl.texImage2D` 以它作为像素源，**同步**把像素拷进 GPU 纹理后，这张 CPU 侧 canvas 就不再被引用。

改法：在 `assertNoGlError` 之后、`uploadedImageKey` 赋值之前，加 `src.width = 0; src.height = 0`，主动释放 backing store（不等 GC）。

为什么安全：`texImage2D` 是同步拷贝，返回时 GPU 纹理已持有完整像素，之后释放 CPU canvas 不影响已上传纹理；`src` 是局部变量，释放它不误伤调用方对象；`assertNoGlError` 在释放前调用，错误检查作用于真实上传。

峰值收益：导出路径（全分辨率 img）上传时，这张 ~192MB 的临时 canvas 不再与后续 `lutCanvas`/`outCanvas` 峰值叠加，省约 192 MB。

## 效果预估（7 张 48MP HEIC）

| 阶段 | 优化前 | 优化后 |
|------|--------|--------|
| 全分辨率解码位图常驻 | 7×192MB = ~1344MB | **0**（导出时才临时解码 1 张） |
| `pixelBlob`（HEIC→JPEG 0.95） | — | 7×~15MB ≈ 105MB |
| `previewImg`（2048 白底 JPEG） | — | 7×~12MB ≈ 84MB |
| **常驻合计** | **~1344MB** | **~190MB（省 86%）** |
| 单张 LUT 导出峰值 | ~900MB | ~200MB（解码 192MB 瞬时 + WebGL + toBlob） |
| 常驻 + 峰值合计 | ~2.5GB | **~400MB** |
| 批量 ZIP 峰值 | > 3GB（炸） | **~600MB** |

> 批量 ZIP 峰值 = 常驻 + 单张导出峰值 + zip 累积 blob。zip 累积 blob 视内容而定（JPEG 压缩后每张约 5~15MB，7 张 35~100MB，可忽略）。

iOS Safari Jetsam 阈值约 2~3 GB，优化后峰值 ~600 MB，远低于阈值，应稳定不闪退。

## 已知取舍（诚实版，review 需知）

1. **HEIC 像素非无损**：HEIC 的 EXIF 仍从原始 HEIC 无损提取/写回，但**像素**经过「HEIC → JPEG 0.95」一次转码（`libheif` 本身只给 8-bit，10-bit/HDR HEIC 高动态范围本就不保，非本次新引入）。0.95 肉眼不可见，但若要 HEIC 像素 100% 无损，`pixelBlob` 需保留 ~120MB 的 PNG，即「内存 vs 无损」的取舍，当前按决定选了省内存。
2. **PNG 导出不含 alpha**：PNG 输入已在源头拍平白底 + 转 JPEG 0.95，故即便用户选 PNG 导出，也不含透明通道，画质上限等于 JPEG 0.95 的源（非原 PNG 无损）。这与「统统非 alpha」一致。
